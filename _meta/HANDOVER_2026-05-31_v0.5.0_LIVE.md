## 3. LLM/Foundry-Pfad — VERIFIZIERT gegen Prod

Echter `POST {endpoint}/v1/messages` mit Prod-Secret → **HTTP 200**, Antwort `model: claude-sonnet-4-6`,
Text `"AEGIRA-LLM-OK"`, `stop_reason: end_turn` (genuine Modellantwort, **kein** Composer-Fallback).

**Prod-Konfiguration (Container App `ca-aegira-planner-api`):**
- `AZURE_FOUNDRY_ENDPOINT = https://api.anthropic.com` — **direkte Anthropic-API**, NICHT Azure-Foundry
  (trotz „FOUNDRY"-Variablenname).
- `AZURE_FOUNDRY_DEPLOYMENT_PRIMARY = claude-sonnet-4-6`.
- Key = Container-App-Secret `foundry-api-key` (`sk-ant-…`).
- `is_configured()` = true → Code nimmt den echten LLM-Pfad. Seam: `app/llm/foundry.py`
  (`complete()` ruft `/v1/messages` mit Header `x-api-key` + `anthropic-version: 2023-06-01`).

**Verifikationsbefehl (vom User im Terminal ausgeführt — Agent darf Prod-Secret nicht lesen):**
```bash
RG=aegira-planner-prod; APP=ca-aegira-planner-api
EP=$(az containerapp show -g $RG -n $APP --query "properties.template.containers[0].env[?name=='AZURE_FOUNDRY_ENDPOINT'].value | [0]" -o tsv)
MODEL=$(az containerapp show -g $RG -n $APP --query "properties.template.containers[0].env[?name=='AZURE_FOUNDRY_DEPLOYMENT_PRIMARY'].value | [0]" -o tsv)
KEY=$(az containerapp secret show -g $RG -n $APP --secret-name foundry-api-key --query value -o tsv)
curl -s -w "\nHTTP=%{http_code}\n" --max-time 60 -X POST "${EP%/}/v1/messages" \
  -H "x-api-key: $KEY" -H "anthropic-version: 2023-06-01" -H "content-type: application/json" \
  -d "{\"model\":\"$MODEL\",\"max_tokens\":64,\"system\":\"Test.\",\"messages\":[{\"role\":\"user\",\"content\":\"Antworte mit: AEGIRA-LLM-OK\"}]}"
unset KEY
```

## 4. Der Deploy-Blocker (gelöst) — wichtige Lehre

**Erster Deploy schlug fehl:** Frontend-Image-Build (`next build`, das im Docker-Image **inkl. ESLint** läuft)
brach ab an:
```
./app/projects/[id]/plan/activities/page.tsx
77:23  Error: `"` can be escaped …  react/no-unescaped-entities
```
Ursache: ein wörtliches `"` im JSX-Text (`tippe auf „?"`). **`tsc --noEmit` prüft kein ESLint** → der Fehler
war lokal unsichtbar und schlug erst im Prod-Build zu.

**Fix:** typografisches Schlusszeichen `"` → `"` (PR #33, 1 Datei, 1 Zeichen). Lokaler `next build` danach grün.

**LEHRE: Vor jedem Push lokal `next build` laufen lassen** (in `$HOME`-Kopie, NICHT aus Dropbox — SWC blockiert),
nicht nur `tsc --noEmit`. Sonst gehen ESLint-Errors erst im Deploy auf.
